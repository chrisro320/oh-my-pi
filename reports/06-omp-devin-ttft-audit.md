# Devin SWE-2：omp 與官方 CLI 首字延遲（TTFT）差異審計報告

**報告日期**：2026-09-13
**核心環境**：Oh My Pi (OMP) + Devin provider（`swe-2-high`）vs 官方 Devin CLI v3000.10.21
**端點**：`https://server.codeium.com/exa.api_server_pb.ApiServerService/GetChatMessage`（Connect over HTTP/1.1）
**資料來源**：`~/.omp/agent/sessions/**`（2,299 筆真實回合）、`~/.omp/logs/omp.*.log`（1,451 筆分段計時）、`~/.local/share/devin/cli/transcripts/*.json`（188 筆官方回合）、`/tmp/omp-devin-fullpath-0913/` 受控實驗

> **重要前提**：本輪全部為唯讀診斷與合成探針。**未修改 omp 正式程式、未改動代理節點或任何網路設定。**
> SWE-2 額度無限，故所有實驗均不受成本約束；本報告不討論成本，只討論**延遲**。

## 3. 請求格式與 TTFT 差距的受控檢驗

### 3.1 方法

- **模板**：`/tmp/devincli-req.pb`（74,379 bytes）＝官方 CLI 原封請求的原始 protobuf，含 `metadata.f`(732 字元)、25 個官方工具、21,268 字元 system prompt、`trajectoryReference`
- **對照**：`omp-interactive.request.pb`＝omp 真實互動請求
- **憑證**：兩臂皆用目前有效的 Devin 憑證；每次呼叫重新簽發 JWT（避免過期導致空回應）
- **公平性**：每次呼叫獨立 `cascadeId`／`sessionId`／`trajectoryId`；交錯順序；驗證 `cacheRead`

### 3.2 結果

**（a）預熱態**（前綴全命中）

| 臂 | n | 首字中位 |
| :--- | ---: | ---: |
| CLI 原封 | 6 | **3.63s** |
| omp | 6 | **4.54s** |

Mann-Whitney **z = −0.16**（不顯著）。

**（b）真冷態**（`cacheRead` 全為 0；以全新 system prompt＋全新工具定義構造，兩臂輸入量對齊）

| 臂 | n | 首字中位 | 輸入 token 中位 | 預填充速率 |
| :--- | ---: | ---: | ---: | ---: |
| CLI 原封 | 4 | **18.6s** | 49,009 | 4,674 tok/s |
| omp | 4 | **12.78s** | 47,664 | 3,812 tok/s |

**逐筆原始值（秒）** — 中位數受離群值影響大，必須連原始值一起看：

| 臂 | 逐筆首字（秒） | 備註 |
| :--- | :--- | :--- |
| CLI 原封 | 8.5 / 10.5 / 26.7 / **73.6** | 含一筆 73.6s 離群（`headersMs` 60.6s） |
| omp | 6.5 / 10.9 / 14.7 / 21.1 | 分布較集中 |

原始資料：`/tmp/omp-devin-fullpath-0913/cold3.events.jsonl`
**「CLI 18.6s vs omp 12.8s」不可解讀為「omp 較快」**——差異由那筆 73.6s 離群主導，兩臂實質無差。

Mann-Whitney **z = 0.58**（不顯著）。

**（c）閘門驗證與快取機制（未定論）**

以「只換 system prompt、保留原工具」為探針時，兩次結果不一致：

| 探針（皆為只換 prompt） | 時間 | input | `cacheRead` |
| :--- | :--- | ---: | ---: |
| cold2 閘門 | 18:37 | 7,686 | **5,197** |
| bust 探針 A | 18:39 | 42,488 | **476** |

**兩次相差 2 分鐘，且 476 已低於本輪採用的冷度判據（<500）。**

因此「只有同時替換 prompt 與全部工具，`cacheRead` 才歸零」**不成立**——bust 探針 B（換 prompt＋換工具）的 `cacheRead` 完全消失（欄位缺席），但探針 A 單獨換 prompt 同樣已接近零。

**可能的解釋（現有資料無法唯一判定）**：

1. 5,197 是工具段仍在 TTL 內的殘留，兩分鐘後自然過期 → **與位置前綴一致**（工具段排在 prompt 之前）；
2. 伺服器按跨段（段雜湊）命中，故僅換 prompt 不足以失效。

**本報告不宣稱任何一種機制已被證明。** 冷度判據仍以「`input`（未命中）量足夠大且兩臂受控」為準，而非要求 `cacheRead` 嚴格歸零。

### 3.3 結論

**在兩種快取條件下，均未觀察到「官方原封請求」相對「omp 請求」的顯著改善。**

必須註明：

- 各臂 **n=4–6，且方差極大**（真冷態 CLI 臂含一筆 73.6s 離群）。
- 因此正確表述是「**未能證實請求格式與 TTFT 差距有關**」，**不是**「已證實無關」。
- 若要下強結論，需擴大樣本至各臂 n≥15，並排除離群或改用穩健統計量。

## 5. 未定論與後續檢驗

### 5.1 未定論

「omp 上下文為 CLI 的 1.28 倍，而冷 TTFT 與上下文成正比 → 1.28 倍正好對應觀測差距」**僅為數值上的吻合，屬相關性，不是因果**。本輪未做「同上下文規模下的乾淨冷啟動對比」。

### 5.2 建議的決定性實驗

僅取**冷回合**、僅取 TTFT，按上下文總量分桶，分別擬合 CLI 與 omp 的 `TTFT-vs-context` 曲線：

- 若同桶內兩曲線**重合** → 差距由上下文規模解釋；
- 若同桶內 omp **仍慢** → 差距另有來源。

（曾有一版 context-matched 對照記到 omp 慢 1.55–2.98 倍，但該版含生成時間、CLI 每桶 n=1–8，不足採信，需重做。）

### 5.3 其他未解

- 為什麼 omp 前綴失效比 CLI 頻繁（兩者前綴內容不同，但格式已證明無關）
- 帳號層級伺服器端狀態
- 官方 CLI `metadata.f` 的語義（**從未偽造，也未落盤**）

## 8. 追加調查（同日稍晚）：延遲歸屬與分片假說

### 8.0 本節觸發的兩個假說，及其下場

| 假說 | 檢驗 | 結果 |
| :--- | :--- | :--- |
| H1：慢是**全局服務端排隊**（同時段兩臂一起慢） | 順序交錯配對 | **否定**（§8.5：`corr=−0.165`） |
| H2：慢由**每請求的服務端指派**決定（含分片） | 併發 K=8 同構請求 | **延遲確由每請求指派決定（確立）；是否為「分片」未證實**（§8.4） |

### 8.1 延遲歸屬（**已更正：原推論量綱錯誤**）

**原稿曾寫「首字 95–99% 是伺服器端時間，依據 `serverLatencyMs/ttftMs ≈ 0.99`」——該推論錯誤，已撤回。**

**為何錯誤**：`serverLatencyMs` 取自**逐幀 `msg.latency` 的最大值**，而 `msg.latency` 是**自請求起算的累計服務端耗時**，因此 omp 完整讀完整條串流時，它取到的是**最後一幀**的值，量綱上貼近 `durationMs` 而非 `ttftMs`：

| 檢驗 | 值 |
| :--- | ---: |
| `corr(serverLatencyMs, durationMs)` | **1.000** |
| `corr(serverLatencyMs, ttftMs)` | 0.625 |
| `serverLatencyMs / durationMs` 中位 | 0.87 |
| `serverLatencyMs / ttftMs` 中位 | 0.99 |
| **`serverLatencyMs` 反而大於 `ttftMs` 的比例** | **48.4%** |

**48.4% 的樣本裡它比首字還大** → 用它比首字是拿整輪時長比首字。**此比值不得再用於歸因。**

**改用純客戶端量測的分段（§2.2，量綱正確）**：

| 階段 | 中位 | 佔 TTFT |
| :--- | ---: | ---: |
| 認證 `authMs` | ~0 ms | ~0% |
| **客戶端量測：等待伺服器首幀到達 `headersMs`** | **4,534 ms** | **61%** |
| 首幀→首字 | 2,190 ms | 30% |
| 合計 `ttftMs` | 7,411 ms | 100% |

`headersMs` 是**客戶端自己計時**（送出發送到 response headers 到達），量綱明確。**結論以它為準：本機（認證＋組包＋TLS）合計 ~0–1.2s，其餘 ~99% 是送出後等待伺服器。**

**注意**：`headersMs` 亦含網路 RTT，不能全歸給伺服器內部處理；只能說「非本機 CPU 開銷」。

### 8.2 必須先排除的混淆：devin 不是單一模型

**這推翻了本節早先「devin 逐時中位 5 倍 regime shift」的讀法。**

| devin 模型 | n | 首字中位 |
| :--- | ---: | ---: |
| `glm-5-2` | 25 | 1.18s |
| `deepseek-v4-1-flash` | 78 | **2.21s** |
| `swe-2` | 2,118 | **7.19s** |
| `gpt-6-astra` | 78 | **10.57s** |

逐時模型組成顯示：09-11T15/16 的「2.2s」時段 **100% 是 deepseek**；09-12T10 的「10.57s」**100% 是 gpt-6-astra**。
**該 regime shift 是換模型，不是服務端劣化。**

**固定在 `swe-2` 內部**，逐時中位仍在 3.79s–10.4s 間擺動（**1.97 倍**）——真實變異存在，但遠小於 5 倍。

### 8.3 跨 provider 對照（證據比原先弱，且**不構成**「devin 專屬劣化」）

改以**固定單一高樣本 provider** 同時段對照（排除成分稀釋）：

| 對照 | 重疊時數 | 相關性 | swe-2 擺幅 | 對照擺幅 |
| :--- | ---: | ---: | ---: | ---: |
| `google-antigravity/gemini-3.8-flash`（n=4,470） | 6 | 0.225 | 1.97x | **2.51x** |

**注意：對照 provider 的擺幅比 swe-2 還大。** 因此只能說「非本機／ISP 問題（屬遠端）」，**不能**據此斷言「devin 專屬劣化」。原 §1「devin 獨有」的措辭已於 §8.6 更正。

### 8.4 決定性實驗：併發 K=8 同構請求

**方法**：8 條請求**同一瞬間發出**，共用 20k 字元相同前綴＋相同工具定義＋`'Reply with exactly: OK'`，僅尾段 seed 不同。

**控制變數**（全部相等或近等）：

| 變數 | 同批次實測離散 |
| :--- | :--- |
| 輸入 token | **0.3–0.4% 散布**（各約 58.6–58.9k） |
| 模型 | 全部 `swe-2` |
| 客戶端 | 同一 process、同一 JWT、同一 TCP 池 |
| 前綴／工具 | 相同 |

**結果**：

| 批次 | n | TTFT 排序（秒） | 中位 | 同批內擺幅 |
| :--- | ---: | :--- | ---: | ---: |
| 0 | 8 | 4.25 / 6.02 / 7.17 / 10.33 / 12.73 / 13.38 / 19.56 / 29.19 | 11.53 | **6.87x** |
| 1 | 8 | 9.99 / 13.27 / 18.67 / 20.96 / 26.78 / 32.98 / 36.88 / 45.47 | 23.87 | **4.55x** |
| 2 | 8 | 9.46 / 10.80 / 12.26 / 12.35 / 12.59 / 27.45 / 31.82 / 42.83 | 12.47 | **4.53x** |

**同一瞬間、同一模型、同一輸入量、同一客戶端 → TTFT 相差 4.5–6.9 倍。**

**這排除了**：

- ✅ **客戶端**（同一 process、同一 JWT、同一連線池）——延遲不可能由客戶端產生如此分散
- ✅ **上下文規模**（輸入量散布僅 0.3%）
- ✅ **模型差異**（全為 `swe-2`）

**這不能排除「共享／全局佇列」（原稿此處推論錯誤，已更正）**：

原稿寫「若共享瓶頸，同批應一致地慢」——**錯**。單一共享瓶頸在併發數 > 容量時，第 k 條自然約於 k×T 完成，**本身就產生 ~N 倍分散**（容量 1–2 即得 4.5–6.9x）。因此本探針的分散**完全可以由單一 FIFO 佇列產生**，不能據此斷言分片。

**另**：同批 `tokPerSec` 對 TTFT **單調遞減**（13,828 → 3,003；5,883 → 1,591），表示慢請求的**整段 prefill 速率都較低**——這與「排在佇列後段」或「分到較慢後端」兩種解釋**都相容**。

**真正指向「非共享瓶頸」的證據（較弱，需標註）**：

| 對照 | n | TTFT 中位 |
| :--- | ---: | ---: |
| K=1（一次一條，順序） | 14 | **19.73s** |
| K=8（同時八條） | 24 | **13.33s** |

**併發 8 條並未比一次一條更慢**（反而更快）。若是單一共享瓶頸，K=8 應顯著劣於 K=1。

**但此對照不乾淨**：兩組上下文不同（K=1 用 90k/260k 字元填充，K=8 用 90k）、時段不同、樣本各僅 14/24。**只能說「與共享瓶頸不一致」，不足以證實分片。**

### 8.5 反證與自我更正（必須並列）

| 我早先的說法 | 實際數據 |
| :--- | :--- |
| 「同時段兩臂一起慢」（5/7 配對同慢） | **`consecutive_cross_arm_corr = −0.165`**（n=7）→ 幾乎無關聯；配對中位間隔 **22.7s**，早已不共享服務端狀態 |
| 「0 組兩臂同快」 | 這是**冷態取樣假象**——樣本最小值 6.5s，本就沒有快尾 |
| 「devin 逐時中位 5 倍擺幅 = 服務端劣化」 | **模型混淆**（§8.2），且同 provider 對照擺幅更大（§8.3） |

**H1（全局排隊）因此否定。**

### 8.6 修正後結論

**已確立（強）**：

1. **本機開銷極小**：以客戶端自計時的分段（§2.2／§8.1），本機（認證＋組包＋TLS）約 0–1.2s，其餘 ~99% 是「送出後等待伺服器首幀」。
2. **同一瞬間發出的 8 條同構請求，TTFT 相差 4.5–6.9 倍**（輸入量散布僅 0.3%、同模型、同客戶端）→ **延遲由每請求的服務端指派決定**。
3. 冷啟動 TTFT 隨上下文總量近似線性（§4）。

**已否定**：

- 請求格式／內容（§3）
- 「同時段兩臂一起慢」式的全局排隊（§8.5：`corr = −0.165`）
- 「devin 專屬劣化」（§8.3：對照 provider 擺幅更大）

**未證實（本次不得斷言）**：

- **是否為「分片」**：K=8 的分散可由單一共享佇列自然產生（§8.4），僅 K=1 中位（19.7s）> K=8 中位（13.3s）與共享瓶頸不一致，但該對照上下文／時段不同、樣本小。**只能說「與分片一致」，不能說已證實。**
- 分片的判別依據（24 筆 `responseId` 前綴 2,267 種/2,299 筆，**無聚集**）
- 為何 `swe-2` 中位（7.19s）系統性高於其他 provider 的 2.9–4.8s

### 8.7 對使用者問題的直接回答

> 「有時候 CLI 快，有時候 omp 快；慢的時候特徵都很像（冷 30s、熱 10+s），是否可能服務端路由問題？」

**方向對：延遲確實由服務端的「每請求指派」決定，本地無可優化空間。但「分片」這一具體機制尚未證實。**

| 現象 | 解釋 | 證據強度 |
| :--- | :--- | :--- |
| 有時 A 快、有時 B 快 | 兩者各自落到**不同的每請求服務端處理路徑／位置**，與是哪個客戶端無關 | **強**——同構併發請求 TTFT 就差 4.5–6.9x |

### 9.4 成因（機制推論，證據等級標註）

**⚠️ 先更正一個方向性錯誤**：原稿寫「CLI 走 h2，而 **h2 多工所以連線更多**」——**這是反的**。HTTP/2 的多工是 **N 條 stream 共用 1 條 TCP**（連線**更少**）；**HTTP/1.1 才是「每個並發請求各開一條 TCP」**。

因此：**觀測到 16 條同刻並發連線，反而是 HTTP/1.1 語義（或刻意的多 socket 池）的特徵，不能當成「走了 h2」的證據。**

（另：本機代理為 TLS 終結型，`openssl` 直連實測伺服器側支援 h2，但**經代理後 CLI 實際協商到的協議未被直接觀測**；`ALPN negotiated h2` 僅是二進位內的字串，不代表本次生效。）

| 機制 | 證據 | 等級 |
| :--- | :--- | :--- |
| **啟動期並發扇出**：CLI 在 ~1.1s 內並發 16 條至同一端點（FD 16–22 同刻 `EINPROGRESS`）→ 更像**每並發請求各開一條**，而非 h2 多工 | syscall 時間戳 | **強**（觀測）／機制屬**推論** |
| **多端點扇出**：CLI 啟動需向 `unleash`（feature flags）、`api/cli/update`、`api/healthz`、plugin/MCP/cloud 等取資料；omp 只打 `GetUserJwt` + `GetChatMessage` | 端點字串 | **中** |
| 協議差異（CLI 含 hyper+h2 棧／omp 走 Connect h1.1） | 二進位字串 + omp 原始碼 | **中**（**但不可用來解釋連線數**，見上） |

**保活機制：兩邊都有，差在觸發方式（原稿「omp 缺此機制」錯誤，已更正）**

| | 官方 CLI | omp |
| :--- | :--- | :--- |
| 機制 | `affogato::cache_keepalive`（`[CACHE_KEEPALIVE] Starting/Stopping keepalive pinging`） | **`/cron` 前綴保活擴展**（`patches/cron-extension.ts`） |
| 觸發 | **自動** | **手動**（`/cron`、`/cron loop<n> <duration>`、`cron({action:"enable"})`） |
| 上限 | 未觀測 | **有界**：`n ∈ [2,100]`，跑完自動 disable |
| 最小間隔 | 未觀測 | **3 分鐘**（`MIN_INTERVAL_MS`） |
| 內建 devin 預設 | — | **有**：`COMMAND_PRESETS.devin = "loop30 4m"`（30 次 × 4 分鐘） |
| 日誌 | — | `~/.omp/agent/cache-keepalive.log`（實測 147 KB、活躍） |
| 刻意非通用排程器 | — | 是（spec 明載） |

**故差異不是「有無」，而是「CLI 自動觸發 vs omp 需手動啟用且有次數上限」。** 且 omp 已針對 devin 的 TTL 選好 `loop30 4m`，與本報告 §3 測得的 6–12 分鐘 TTL 相符。

**未證實**：

- 各條連線的**具體用途**（未取得 CLI 的 HTTP 層 debug 日誌：`RUST_LOG=debug` 與 `DEVIN_LOG=debug` 皆未產生輸出；`~/.local/share/devin/logs/` 為空）
- 本次經代理後**實際協商到的協議**（h1.1 或 h2）
- 16 條是「並發請求」還是「刻意預熱的連線池」
- 是否對 TTFT 有影響——**§8 已證延遲由服務端每請求指派決定，與本機連線數無因果**

### 9.5 對使用者問題的直接回答

> 「devin CLI 啟動時產生的連線數量明顯高於 omp，為什麼？」

**觀測事實（強）**：同一回合內，CLI 對 `server.codeium.com` 發起 **16 次 `connect()`（1.1 秒內並發）**，omp **僅 1 次**。

**成因（依證據強度排序）**：

1. **啟動期並發扇出（最可能）**：16 條在同刻並發，是**「每個並發請求各開一條 TCP」**的樣態——這正是 **HTTP/1.1** 的語義（**不是** h2 多工；h2 會把 N 條 stream 疊在 1 條 TCP 上）。CLI 啟動時平行打多個端點／多個初始化請求，故連線數高。omp 序列化地只打必要的兩個 RPC。
2. **多端點初始化**：CLI 要取 feature flags（`unleash`）、檢查更新（`api/cli/update`）、健康檢查（`api/healthz`）及 plugin/MCP/cloud 狀態；omp 無此類啟動流程。
3. **保活連線**：**兩邊都有前綴保活**（CLI 自動 `cache_keepalive`；omp 手動 `/cron`），但 omp 的保活需手動啟用且**有次數上限**（`loop<n>`，n≤100），並非常駐 ping。

**三者疊加 = 面板上的 19 條。**

**另須注意**：omp **不可能**產生 `unleash.codeium.com` 連線（原始碼無此字串）——面板上那兩條必屬 CLI 或 IDE 外掛（`devin-desktop`、`language_server` 亦為常駐候選）。

**這與 TTFT 差距無因果關係**（§8 已證）。

**⚠️ 但這不能推論出「CLI 保活從未運行」——那是我先前的過度推論，已撤回。**

**理由：三次嘗試全都沒有真正進入保活會運作的場景。**

| 嘗試 | 預期場景 | 實際結果 |

**故正確表述是：「在本次測試到的三種模式下，皆未觀測到 ping；而那唯一可能觸發 `lead_idle` 保活的模式（互動回合後閒置）尚未被成功執行。」**

**這一條是本次調查最關鍵的未測缺口**——沒有它，「omp 是否能對齊 CLI 保活」無從判斷（見 §10.5）。

**`shape=Continue`、`my_gen`/`old_gen`、`max_pings` 僅為結構觀測**（`cache_keepalive.rs:494` 等），**實際週期行為未取得**。

**附帶收穫**：互動探針的日誌顯示 CLI 啟動時對 **`unleash.codeium.com` 發出 15 次請求、`remote config fetch finished in ~950–1690ms`（ok: true）**——證實 §9 的 feature-flag 推論。

### 10.3 omp `/cron`：實測行為

| 項目 | omp `/cron` |

### 10.5 能否對齊？—— **尚無法判斷（觀測缺口未補）**

**⚠️ 前設更正**：先前寫「CLI 保活從未運行、故無可對齊的目標行為」——**該推論已撤回**（§10.2）。實情是**三次嘗試都沒進入保活會運作的場景**，其中唯一可能觸發 `lead_idle` 保活的「互動回合後閒置」因探針失敗而**未被執行**。

**因此本節的正確結論是：CLI 保活的實際行為未知，對齊與否無從評估。**

**已知的結構差異（僅結構，非行為）**：

| 特性 | CLI | omp | 狀態 |
| :--- | :--- | :--- | :--- |
| 機制存在 | 有（`affogato::cache_keepalive`） | 有（`/cron` 擴展） | ✅ 對等 |
| 觸發 | 自動（綁 agent 生命週期） | 手動 | ⚠️ 不同 |
| 請求形狀 | **`shape=Continue`**（延續 trajectory） | `runIdleEphemeralTurn`（同 session） | ⚠️ **形狀不同** |
| 世代防護 | `my_gen` / `old_gen` | `scheduledSessionId` 比對 | ✅ 等效 |
| **實際 ping 週期** | **未觀測到（場景未達成）** | 實測 4.2 分鐘、有界 n≤100 | ❓ **無法比較** |
| **實效** | **未知**（日誌無 `cacheRead`） | **雙峰**：hit 808 token / miss 126k 全量 | ❓ **無法比較** |

**omp 保活的實效（唯一有數據的一方）**：

- **雙峰**：命中時 input 中位 808 token（快取 171k）；失效時 126k 全量 prefill、`durationMs` 中位 **14.2s**
- 累計浪費 **5,264,031 token**
- 命中率與間隔**無關**（4.1 vs 4.3 分鐘）
- 逐時成塊變化（12 時段 **0%**、13 時段 **14%**）

**目前可說的**：

1. **omp 側的保活確實有效但間歇**——失效呈分鐘級區塊，**同內容同間隔整段翻轉**，屬服務端狀態而非本地缺陷；
2. **CLI 側行為未知**——在補上「互動回合後閒置」觀測前，**不應斷言 CLI 的自動保活優於 omp**，也不應斷言等效；
3. omp 的 spec **明確禁止**將 `/cron` 擴為自動排程器。

**建議**：**先補觀測再決定**。具體做法＝在互動模式成功跑完一回合後，讓行程閒置 ≥20 分鐘，觀察 `Ping sent` 是否出現及其間隔。若屆時仍未出現 ping，則「對齊」一事即可結案為「CLI 亦無實際保活，無需對齊」。

### 10.6 保活不是本地瓶頸

**omp 保活的成敗由服務端狀態決定，非本地設定**：

- 同內容、同間隔、同 session → 結果兩極（快取比例 0.999 vs 0.0）
- 命中率與間隔無關（4.1 vs 4.3 分鐘）
- 翻轉呈**分鐘級區塊**，非單請求隨機（§10.4）

**故「自動 vs 手動」的差異，即使存在，也不是 omp 冷啟動問題的根因；根因在服務端狀態。**

### 10.7 未證實

- **CLI 保活的實際 ping 週期**——**關鍵缺口**：`lead_idle` 場景（互動回合後閒置）**未被成功執行**（探針 `GetChatMessage=0`）
- **CLI 保活的命中率**——其日誌不含 `cacheRead`，無法量測
- `shape=Continue` 與 `runIdleEphemeralTurn` 在**快取前綴上的等效性**——未做對照實驗
- CLI 保活究竟在何種情境下才會真正 ping
- 「保活 → 下一輪為暖」的**因果性**（§10.4b：現有數據僅為內生相關，無對照組）

## 12. 反例：payload 模型解釋不了的單輪（session `01a0a037-250b-7000-bea8-af0f88beb3e0`）

### 12.1 事實

使用者在此會話只發了 `test`（**該 pid 全程僅此一輪**，`omp.2026-09-14.4194132.log`）：

| 項目 | 值 |
| :--- | :--- |
| 請求大小 | `requestBytes` 100,817 → `compressedBytes` 41,794 |
| tools | 13 |
| `input` | **24,718** token |
| `cacheRead` | **0**（全冷，首次呼叫） |
| 使用者輸入 | `test`（3 字元） |

**分段計時（`devin: turn timing`）**：

| 分段 | 值 | 佔 `ttftMs` |
| :--- | ---: | ---: |
| `authMs` | 742 ms | 1.3% |
| **`headersMs`** | **30,695 ms** | **54.1%** |
| `firstFrameMs` | 30,696 ms | 54.1% |
| `serverLatencyMs` | 56,345 ms | 99.3% |
| **`ttftMs`** | **56,731 ms** | 100% |
| `durationMs` | 57,727 ms | — |

**`headersMs` 之後到首 token 又等了 26,035 ms。**

### 12.2 為何這是 payload 模型的明確反例

依 §1 實測吞吐 **4,000–4,700 tok/s**，24,718 token 全冷 prefill 應為：

$$\frac{24718}{4700} \approx 5.3\text{ s} \quad\text{—}\quad \frac{24718}{4000} \approx 6.2\text{ s}$$

**實際 `ttftMs` = 56.731 s，偏差 9.2×–10.8×。**

**更關鍵**：`headersMs` 30,695ms 佔首字延遲 54%——**這是「伺服器連回應標頭都還沒發出」的時間，發生在任何 token 處理之前**。payload 大小無法解釋「請求尚未被受理」的 30.7 秒。

### 12.3 結論

**payload 量不是唯一解釋**。至少存在兩類獨立成因：

| 成因 | 證據 | 是否本地可影響 |
| :--- | :--- | :--- |
| **① payload / prefill 量** | §11.2：`corr(input, duration)=+0.894`；126k 全量 14.2s vs 32k 暖 5.7s | ✅ 前綴命中率、上下文量 |
| **② 伺服器受理前排隊** | §12.1：24.7k 全冷卻耗 56.7s，其中 `headersMs` 30.7s（54%） | ❌ **不可**（`authMs` 僅 742ms、本地傳輸已對齊 §8） |

**此例（②）與 §11 的量（①）並存，不可用其一抹除另一。**

**前綴命中與 payload 縮減只能在 ① 上生效**；② 類延遲為伺服器受理前的排隊，本地無槓桿。
