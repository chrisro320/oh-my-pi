# 升級預檢設計

## 隔離邊界

正式安裝與 ~/.omp/agent 保持不動。以官方 npm 包建立獨立 sandbox，使用 controller 列出的 18.2.10 計畫作為補丁能力清單。不得讓既有版本 fail-closed gate 為了預檢而放寬，也不得將新版包安裝到全域。

## 判定契約

分類矩陣每列包含：補丁 ID、實際 candidate 路徑、觸及套件/符號、前置依賴、上游對應變更、主要分類、證據、後續動作。

- 可沿用：不只文字可套用，還需相關行為證據。
- 需適配：能力仍需要，但上下文/API/生命週期不同。
- 上游已修可退役：新版原生行為滿足既有契約，提供源碼與驗證，不以命名消失判定。
- 語義衝突：新版設計與本地政策不同，交使用者決策，不能私自刪功能。
- 證據不足：明示阻礙與下個驗證動作，不偽裝成通過。

逐層重放的某個下層失敗可能造成連鎖失敗；須區分直接衝突與前置層未產生造成的衍生失敗。

## 取捨

固定 18.3.3，不在調查中追逐移動的 latest。不新增 supersede 鏈，不改舊版回退基線。先做預檢而非直接部署，代價是增加一次方案確認，但避免把語義衝突留到 live 才發現。

## 後續部署邊界（尚未授權）

預檢通過不等於部署通過。真正遷移需另行完成新版完整 pristine 重放、相關行為驗證與新程序冒煙，確認備份及回滾方案後才切換。任何 SQLite 備份須用 online backup API；不以 filesystem 熱複製代替。舊進程不會因 /resume 載入新程式。
