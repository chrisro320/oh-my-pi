## sidecar 變動與安全結論

- backup 測試期間 `agent.db-wal` 與 `agent.db-shm` 的 inode／size 未變，但 mtime 與 SHA-256 改變；這只能證明觀測窗內 live sidecar 狀態變動，不能歸因於其他程序或 backup。
- 後續只讀觀測 2 秒內，`agent.db-wal`／`agent.db-shm` 再次 mtime 與 SHA-256 改變；同樣不作因果歸因。
- sandbox `PRAGMA integrity_check` 仍為 `ok`，但 live sidecar 非靜止且尚未確認唯讀方法本身不改 sidecar，使本次 backup **不構成完整 strict DB safety gate**。
- 結論：在確認 live DB／sidecar 來源靜止，以及確認唯讀方法本身不改 sidecar 前，禁止再次對 live DB 開連線；也禁止 restore、migration、usage smoke 或新版啟動，不得把本次結果標為 DB safety acceptance PASS。

## apply.sh 版本選擇機制驗證（2026-08-30，全 sandbox，/tmp 隔離）

### 機制審查與修正

- 審查未提交的 `OMP_PATCH_VERSION` gate：`${OMP_PATCH_VERSION+x}` 把空字串視為 set → fail-closed（exit 2）；`18.0.9` 純 no-op；`18.0.11` 同時要求 installed `pi-coding-agent/package.json` version == 18.0.11 且 candidate 檔案存在，否則 exit 2；其他值（含空字串、未知版本）exit 2。語義正確，未改動。
- 發現並修正一個順序 bug：原實作 version gate 落在 `--verify-rollups` exec 之前，未知/空 `OMP_PATCH_VERSION` 會讓 rollup 閘門被無關的 exit 2 擋掉，且 NOTE 輸出會污染 rollup 紀錄。最小修正：把 `--verify-rollups` exec 移到 version gate 之前（comment 一併歸位）。`--verify-rollups` 因此完全不讀 `OMP_PATCH_VERSION`。
- 修正後 sandbox 驗證：`OMP_PATCH_VERSION=19.9.9 --verify-rollups` 仍正常輸出 `PASS static`／`PASS baseline`；`--check` 同 env 仍 exit 2 fail-closed。預設（unset）行為不變：canonical 0010 照舊。
