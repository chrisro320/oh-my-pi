### Description

When several isolated tasks (`isolated: true`, `task.isolation.merge: patch`, the default) finish at about the same time and their patches touch the same file, merge-back loses edits. Most of the lost edits are still reported as `Applied patches: yes`, so neither the parent agent nor the user can tell. The rest come back as "not applied" even though each patch applies cleanly when the patches are applied one after another.

Each subagent merges as soon as it finishes (`structured-subagent.ts` ~1106-1118 → `mergeIsolatedChanges`). Patch mode then runs `canApplyPatch(reverse)` + `canApplyPatch(forward)` + `applyPatch` against the parent worktree (`task/isolation-runner.ts` ~741-786) with no repository lock. Concurrent `git apply` runs on the same file each read the file, apply their hunk and write the whole file back, so the last writer wins. Branch mode already serializes merges with `withRepoLock(repoRoot, …)` (`task/worktree.ts` ~1064-1065, "background merges would race on HEAD and the index"); patch mode has no equivalent.

`isolation-runner.ts` on `main` (last change 3894f9124a, "added ovnfs as an isolated checkout backend") is byte-identical to the 18.18.0 file I tested, so this should still apply to v18.18.1.

### Steps to Reproduce

**In omp:**

1. Enable `task.isolation.enabled: true`. Leave `task.isolation.merge` at its default (`patch`).
2. In a git repo, have a file with 8 (or 32) lines that are well separated (at least 7 lines apart, so the patches don't share context).
3. Launch 8 (or 32) parallel isolated tasks in one `task` call. Each task edits a different one of those lines in that same file and finishes at about the same time.
4. Check the file after all tasks return, and compare it with each task's merge summary.

Results: I drove this through the SDK with a scripted offline model, with `isolation.backend: auto` resolving to the ovnfs backend (ovnfs v0.2.3). Each task's checkout was correct: one checkout per worker, one-line diff, no leak into the parent before merge. Only the merge-back lost data. 3 sets of runs (5 + 2 + 5):

| workers | edits missing from the file per run | of those, reported `Applied patches: yes` |
|---|---|---|
| 8 | 2–7 | 2–5 |
| 32 | 12–22 | 11–21 |

With every task editing a *different* file, all edits landed (8/8 and 32/32, every run).

**Without omp:** this script applies one-line patches the same way `mergeIsolatedChanges` does (reverse check, forward check, apply), started all at once (`parallel`), one after another (`serial`), or serialized with `flock` (`locked`):

```bash
#!/usr/bin/env bash
set -euo pipefail
N=${1:-8}
MODE=${MODE:-parallel}
dir=$(mktemp -d)
trap 'rm -rf "$dir"' EXIT
cd "$dir"
git init -q repo && cd repo
for i in $(seq 0 $((N * 10 - 1))); do echo "line $i"; done > shared.txt
git add shared.txt && git -c user.email=t@t -c user.name=t commit -qm base
for i in $(seq 0 $((N - 1))); do
  sed "s/^line $((i * 10 + 5))\$/edited by worker $i/" shared.txt > ../w$i.txt
  git diff --no-index shared.txt ../w$i.txt | sed "s#b/../w$i.txt#b/shared.txt#" > ../p$i.patch || true
done
apply_like_omp() {
  local p=$1
  if git apply --check --reverse "$p" 2>/dev/null && ! git apply --check "$p" 2>/dev/null; then
    echo "already-applied"; return
  fi
  if git apply --check "$p" 2>/dev/null; then
    git apply "$p" 2>/dev/null && echo "applied" || echo "apply-failed"
  else
    echo "not-applicable"
  fi
}
for i in $(seq 0 $((N - 1))); do
  case "$MODE" in
    parallel) apply_like_omp ../p$i.patch > ../res$i & ;;
    locked) (flock ../apply.lock bash -c "$(declare -f apply_like_omp); apply_like_omp ../p$i.patch" > ../res$i) & ;;
    *) apply_like_omp ../p$i.patch > ../res$i ;;
  esac
done
wait
echo "$MODE N=$N reported applied: $(cat ../res* | grep -c '^applied$')/$N, edits present: $(grep -c '^edited by worker' shared.txt)/$N"
```

### Expected Behavior

Every patch that applies cleanly on its own should land when parallel isolated tasks merge back, as it does when they merge one at a time. A summary should never say `Applied patches: yes` for an edit that isn't in the parent worktree.

A likely fix is to run the patch-mode check-and-apply in `mergeIsolatedChanges` (and the nested-patch apply) under the same `withRepoLock(repoRoot, …)` that branch mode already uses. With the lock emulated by `flock` in the script above, 32/32 land in 3 of 3 runs.
