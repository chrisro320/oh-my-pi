## 3. Anthropic threads adoption

Answers Main's three questions.

### 3.1 What marks a message per-call today

The only guard is `anthropic.ts:2261`: `!context.messages.some(message => isPerCallContextMessage(message))` (inside the `threadTurn` condition `:2256-2266`). Producers in the 18.18 tree:

1. `ExtensionRunner.emitContext` — `agent/extensibility/extensions/runner.ts:2416-2424`: after all `context` handlers run, every message that is not byte-equal (`Bun.deepEquals`) to its stored-history counterpart is marked. So ANY extension whose `context` handler rewrites a message marks it on every call. (0074's own note P-74 / PATCHES.md:1678: the marker means "differs from stored JSONL", not "differs from the previous request".)
2. `agent-session.ts:13409, 13424, 13436, 13441, 13451` — `#buildEphemeralSnapshot` for side turns (`runEphemeralTurn`, `:13169`). Those use `sideSessionId = ${cacheSessionId}:side:…` (`:13255-13257`), a separate chain, so they never touch the main thread chain. They are irrelevant for main-thread suppression.
3. `agent/job-widgets/author.ts:218`, `caption.ts:91` — one-shot side completions with a single message; no session thread.

Extensions in `~/.omp/agent/extensions/` (all read): the only `context` handler is `context-persist-audit.ts:292`, which returns `undefined` on every path (`:292-324`) and skips `purpose === "side-request"`, so it marks nothing. `cache-prefix-audit.ts:930`, `payload-archive.ts:99`, `resume-cache-breakpoint.ts:468` are `before_provider_request` hooks, not context hooks. No patch under `patches/` calls `markPerCallContextMessage` (grep: only `verify-anthropic-cache-boundaries.ts:28,53,118` use it as a fixture).

Trellis: the 0016 injector is the `context` handler at `.trellis/legacy-omp/extensions/trellis/index.ts:758-864` (rewrites the newest user message every call, byte-stable per anchor). It was retired for `omp-move` only (DECISIONS "omp-move 停用 Trellis", 2026-11-07, which explicitly leaves other projects alone). The glob `~/orca/projects/*/.omp/extensions/*` still finds `人山/.omp/extensions/trellis/`. Conclusion: in `omp-move` no producer marks main-loop messages, so threads WILL be active there; in `人山` (and any project that still carries Trellis) the guard keeps suppressing threads, which is exactly the 18.16 behavior.

### 3.2 What threads change for 0074 / 0094 / 0092 / audits

Facts first. Threads need `providerSessionState` + `options.sessionId` + official endpoint + `compat.supportsMessageThreads` (`anthropic.ts:2256-2262`; `anthropic-threads.ts:140-150`; catalog rule `classes/anthropic.kdl:220` in `pi-catalog/src/compat/rules.json`, models >= 4.5.0). Token usage and pricing are unchanged by threads (`anthropic-threads.ts:6-7`), so the benefit is latency (TTFT) only; cache accounting should not change. A continue sends only `messages.slice(anchor.messages.length)` through `continueBreakpoints` (`anthropic-threads.ts:230-234, 419-455`) and deletes `system`/`tools` unless OAuth (`:235-238`; `resendSystemAndTools: isOAuthToken`). `plan()` runs at `anthropic.ts:2671` per attempt, AFTER `onPayload` (`:2321`). The chain lives in `providerSessionState.threads` (in memory; a restart or `/resume` starts with a create). Anchor reuse window is 270 s (`:56`).

* **0074 message breakpoints.** The create body is the unmodified full `params` (`anthropic-threads.ts:241`), so 0074's breakpoint placement is exactly what the server sees on every create. On a continue 0074's breakpoints on the held prefix are dropped from the wire and replaced by upstream's (first appended block + newest, `:419-455`). 0074's design is therefore preserved for creates and superseded by upstream's measured design for continues. Anything the user cares about re: hit-rate on continues is now upstream's contract, not ours.
* **Prefix-drift detection becomes a silent fallback.** `extendsConversation` (`:354-378`) compares full messages ignoring `cache_control`; any drift in held history makes the next request a create instead of a continue. Nothing errors. So thread hit-rate is itself a prefix-stability signal (useful gate input, R2) but also means drift no longer shows up as latency regressions for the user.
* **0074 audit (`anthropic-request-audit.ts`, fetch wrap).** Wraps `fetch`, so it records the real wire body (P-74:142-207). With threads, a continue body has only appended messages, no `system`/`tools` (API-key mode), plus `thread` field. `wrapFetch` writes `.baseline.json` for every non-compact, non-side, non-refresh request (P-74:187-191), so after one continue the baseline points at a truncated body. The next native compaction compares `before.tools`/`before.system`/`messages[i]` against it (P-74:175-181) and reports `prefix-different` falsely. Required change: record `body.thread?.type` in `.meta.json`, skip baseline updates for `continue` bodies (the last create body is a valid prefix because the comparison allows tail appends, P-74:178), and add a `thread` kind to the report. Small, but without it the audit lies.
* **`before_provider_request` extensions** (`cache-prefix-audit.ts`, `payload-archive.ts`, `resume-cache-breakpoint.ts`) fire inside `prepareParams` at `anthropic.ts:2321`, before `plan()`. They still see the full logical body, not the wire body; their archives remain valid prefix-drift records but are no longer "bytes sent". `resume-cache-breakpoint`'s injected breakpoint matters only on creates, and the first request after resume is always a create (chains are in memory), so it stays correct.
* **0094 (thinking-drop persistence).** Retry ladder rebuilds `params` and `plan()` is called again per attempt (`:2671`, same-params memoization `:216-217`). A dropped thinking block changes held messages, so the next request is a create. Compatible [INFERENCE: not run].
* **0092 cache warming (`/cron`, native warmer).** The warm replay is built from `run.options` of the last request (`agent/session/cache-warmer.ts:761-775`: same `sessionId`, same `providerSessionState`, `maxTokens: 1`). Its messages equal the anchor's messages minus the stored reply, so `extendsConversation` is false and it is planned as a CREATE (`anthropic-threads.ts:240-241`); it finishes with `stopReason: "length"`, which is not `continuable` (`anthropic.ts:3745-3749`), so `settle(undefined)` sets `chain.anchor = undefined` (`anthropic-threads.ts:304`). Result: every warm ping erases the session's thread anchor and the next real turn is a full create. No billing effect, but threads would be defeated for any session with `/cron` keepalive shorter than the 270 s window. Also the audit gate at `verify-anthropic-request-audit.ts:222` documents that a warm replay "keeps the live session identity", which is why this happens. Fix: warm requests set `statefulResponses: false` (same switch upstream's `bench-cli.ts:1252,1273` uses for cache measurement) or reuse a `:warm` session id.
* **Compaction / summarization requests (family-compaction).** `compact()` is called with `sessionId: options?.sessionId ?? this.#host.sessionId()` and `providerSessionState: this.#host.providerSessionState` (P-comp:4082-4090; advisors use their own `advisorProviderSessionId`, P-comp:3791). Native Anthropic compaction carries `params.compaction` and is explicitly unthreadable (`anthropic-threads.ts:322`). But 0035's cache-preserving summary context is deliberately "live prefix + summarization prompt", i.e. it EXTENDS the main anchor. A non-native summary request using the main session id would be planned as a `continue` from the main anchor, claim it (`anthropic-threads.ts:228-229`), and settle a new anchor made of the summary conversation; a speculative compaction running concurrently with a main turn would continue the same `previous_message_id` twice, which the server refuses ("already continued"), and two refusals disable threads for the session (`:263-271`). Not a correctness bug (any doubt costs a full upload), but silent and avoidable. Fix: pass `statefulResponses: false` (or a distinct `:compaction` session id) in the compaction stream options built by our `session-maintenance.ts` hunks. This is [INFERENCE] until a fixture proves the main anchor is stolen; the gate below is that proof.
* **Worker threads.** `providerSessionState.threads` is per worker [INFERENCE]; subagent chains are independent of main. No change.

### 3.3 Gates proving cache reuse under threads

Existing gates do NOT cover threads: `verify-anthropic-cache-boundaries.ts` has no `sessionId`/`providerSessionState` (grep: no match), `verify-anthropic-request-audit.ts:70` passes `sessionId` but no `providerSessionState`, so `threadTurn` is `undefined` (`anthropic.ts:2259`). They stay green and prove nothing about threads. New gates (offline, fake fetch/SSE, same style as the existing ones; the actual cache-read effect of a continue is a server behavior that offline fixtures cannot prove, so report it as "request construction only" and let a user-approved live probe measure `cacheRead` on a continue turn):

1. `verify-anthropic-threads-cache-shape.ts` — official `claude-opus-5`, `providerSessionState`, `sessionId`: turn 1 is `thread:{type:"create"}` with 0074's breakpoint layout on the full body; turn 2 is `continue` with `previous_message_id` equal to turn 1's `message_start` id, appended messages only, <= 4 breakpoints counting system/tools; turn after `>270 s` (fake clock) is a create. Negative controls: thread with a per-call-marked message must be unthreaded (upstream guard); mutate one held byte and require a create.
2. `verify-anthropic-threads-warm-compaction-isolation.ts` — (a) a warm replay (`maxTokens:1`, live session id) must not clear the main anchor; (b) a 0035 cache-preserving summary request must not claim or replace the main anchor; (c) a native compaction request is unthreaded and leaves the anchor. Fails on the unpatched shape (this is the proof of the conflicts above).
3. Extend `verify-anthropic-request-audit.ts`: a continue body must not become the baseline; native compaction after a create+continue must report `prefix-equal`.

### 3.4 Recommendation

**Adopt threads (default on) and do not touch the guard at `anthropic.ts:2261`.** Concrete reasons:

* The user's rule is adopt unless there is concrete conflict evidence. The only blocking producer in `omp-move` (Trellis, 0016) is retired there; where it survives (`人山`) the upstream guard already falls back to the exact 18.16 unthreaded path, so no regression.
* Relaxing the guard to content-based (the content check in `extendsConversation` would allow it) buys only TTFT, because pricing/tokens are unchanged, and costs a rule that is also protecting against hooks that rewrite per call. Not worth a patch hunk. Revisit only if someone wants threads inside Trellis projects.
* Required work (all small, none in upstream's thread code): (1) audit baseline fix in 0074 (3.2); (2) `statefulResponses:false` for warm and compaction/summary requests (0092 and family-compaction `session-maintenance.ts`); (3) the three gates (3.3). Total effort M.
* The concrete conflict evidence (anchor erased by warm replay; anchor stolen by a cache-preserving summary; audit baseline truncated) is each fixed locally. None justifies disabling threads globally. Fallback knobs if a gate fails and cannot be fixed: `PI_ANTHROPIC_MESSAGE_THREADS=0` or `statefulResponses:false` (`anthropic-threads.ts:140-150`; compat key `statefulResponses` in `agent/config/models-config-schema-bundle.ts:84`).
